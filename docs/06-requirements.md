# 6. Requirements Specification

This section lists the functional and non-functional requirements of Testora, their priority, and how each one is checked. Every requirement has an acceptance criterion that can be tested (automated test, scripted manual check, or measurement). The **Status** column was checked against the public repository (`RakhatBalga/Testora`, branch `main`, October 2026):

- **Implemented** – code is in the production path (backend router + frontend route) and reachable by users of https://testora.studio.
- **Implemented (gated)** – the backend exists, but the UI hides the feature on purpose.
- **Research** – the code exists in `backend/ml/` with unit tests, but it is not connected to the user flow.
- **Planned** – not implemented yet.

Priorities use MoSCoW (**M**ust / **S**hould / **C**ould). Owners: **RB** = Rakhat Balgabekov, **NT** = Nurhan Turganbek.

**Evidence basis.** Requirements come from the product hypothesis (Section 1) and the analysis of existing systems (Section 4). Five user interviews (Section 2) confirm the core Writing loop: Writing is the hardest part for 4 of 5 respondents (F1), and chatbot feedback does not track repeated mistakes (F3). Requirements not discussed in the interviews are marked *"not confirmed by interviews"*.

## 6.1 Functional requirements

| ID | Requirement | Priority | Acceptance criterion | Status | Owner |
|----|-------------|----------|----------------------|--------|-------|
| FR-1 | **Account registration and login.** The user can register with a username and password (minimum 8 characters) and log in to receive a JWT. | M | `POST /auth/register` followed by `POST /auth/login` returns an access token. A password shorter than 8 characters is rejected in the UI. A duplicate username shows the "account exists" dialog. Protected routes redirect to `/login` when there is no token. | Implemented | RB |
| FR-2 | **Google sign-in.** The user can sign in with Google using OAuth 2.0 Authorization Code + PKCE (S256). Only a verified Google email is trusted. | M | `test_google_auth.py` passes: PKCE challenge sent, state is single-use, redirect URI must match exactly, unverified email is rejected, provider failures do not create accounts. Manual check: the Google button completes the flow on production. | Implemented (backend + UI component). The button renders only when `NEXT_PUBLIC_GOOGLE_CLIENT_ID` is set at build time, and it was **not visible** on the live login page when screenshots were taken (Section 8) | RB |
| FR-3 | **Learner profile and goal.** The user can set target band, current level, exam date, weekly study days and primary focus. The target band defaults to 7.5. | M | `PATCH /auth/me` saves each field and `GET /learning/dashboard` shows target band, current level and exam countdown. `test_target_band.py` passes: only half-band targets are accepted, the target cannot be below the current level, and the exam date cannot be in the past. | Implemented | RB |
| FR-4 | **Writing Task 1 / Task 2 submission.** The user picks a task (Academic Task 1 with a rendered chart/table/map, or Task 2 essay), writes a response and submits it. | M | Task list loads from `GET /writing/tasks`. The text is stored. Responses above `MAX_WRITING_CHARS` (20,000) are rejected. Empty, non-English, too-short or meaningless input gets a zero-band pre-check result without calling the LLM (`test_writing_precheck.py`). Off-topic essays are handled by the examiner's cap instead. | Implemented | RB |
| FR-5 | **LLM grading on 4 IELTS criteria.** Each valid Writing submission is graded by the LLM examiner (Gemini, temperature 0.1) and receives an overall band and four criterion bands (TA/TR, CC, LR, GRA) in 0.5 steps. Hard caps apply (missing overview, under-length, off-topic, fabricated data). | M | The response contains `band` plus four criteria, each a multiple of 0.5 in [0, 9]. `test_writing_examiner.py` and `test_gemini_grading.py` pass (normalisation, caps, schema handling). Accuracy against expert scores is evaluated separately (Section 9, E1). | Implemented | RB |
| FR-6 | **Mistake extraction.** Grading returns concrete mistakes (category, sub-skill, severity 1–3, snippet, correction), which are saved to the user's mistake history. Coach evidence is checked against the essay text. | M | After a graded submission, rows exist in `mistakes` linked to the submission. Each snippet appears verbatim in the essay (`sanitize_coach_evidence`). Re-grading replaces the old mistakes instead of duplicating them. | Implemented | RB |
| FR-7 | **"Better Version" rewrite.** The system generates a higher-band rewrite of the user's essay and shows it next to the original with highlighted changes. | S | `improved_text` is filled when the rewrite succeeds. If it fails, the grade is still saved and the UI shows its deterministic diff instead. "Your Response vs Better Version" is visible on `/writing/result/[id]`. | Implemented | RB |
| FR-8 | **Weakness engine (Mistake Memory).** Mistakes are combined into weakness scores with exponential recency decay (half-life 14 days), normalised by the number of opportunities. A weakness is "recurring" when it appears in ≥ 3 recent attempts. | M | `GET /analytics/weaknesses` returns scores in [0, 1). A 14-day-old mistake weighs 0.5 of a new one, and the recurring flag requires ≥ 3 submissions. Related behaviour is covered by `test_weekly_analytics.py` and `test_recommendations.py`. A dedicated unit test for `recency_decay` and the recurring threshold is **planned** (Section 9). | Implemented | RB |
| FR-9 | **Band gap and main blocker.** The system computes overall band (mean of skill bands rounded to 0.5), gap to target, lowest skill, and the named blocker (lowest Writing/Speaking criterion with a band cap and an explanation taken from real mistakes). | M | `GET /analytics/band-gap` and `/analytics/blockers` return these values. The Analytics page shows "Main limiter" with a link to a fix task. With no data the response has `has_data=false` and no invented values. | Implemented | RB |
| FR-10 | **Task for today and weekly study plan.** The dashboard shows one task for today with a reason and time estimate, plus a weekly plan that the user can complete, skip, recalculate or reset. Every task names the signal that produced it. | M | `GET /learning/dashboard` returns `today` with `reason`, `minutes`, `href`. `PATCH /learning/study-plan/{id}` changes status. `test_personalized_learning.py` passes (the weekly plan is idempotent and keeps completed items; it refreshes on a new result; the diagnostic level is applied only after the user confirms it). *Supported by interviews: daily use before the exam, study calendar (Section 2, F6, F9).* | Implemented | RB |
| FR-11 | **Regrade and band change.** The user can submit again, retry a failed review, and compare attempts to see how the band and criteria changed. | M | `POST /writing/submissions/{id}/retry` works only for `failed` submissions (409 otherwise, `test_writing_retry.py`). `/history/compare` shows the band/criterion delta between two attempts. `GET /analytics/progress-impact` returns the recent Writing movement. | Implemented | RB |
| FR-12 | **Reading exam with automatic checking and verbatim evidence.** Timed Reading tests (10 content packs) are scored automatically and converted to a band. The review shows for each question the correct answer, an explanation and the evidence span quoted verbatim from the passage. | M | `POST /results/submit` returns score, band and per-question-type breakdown. The content validator (`validate_reading.py`) confirms every evidence span is an exact substring of its passage. `test_reading_scoring.py` and `test_reading_catalog.py` pass. | Implemented | NT, RB |
| FR-13 | **Listening exam with audio, progress saving and automatic checking.** The user takes a Listening test with an audio player, the position and answers are saved, and the test is scored with an answer review. | M | `PUT /listening/tests/{id}/progress` restores position after reload (frontend `progress.test.ts`). `POST /listening/tests/{id}/submit` returns score and band. `validate_listening.py` checks the real audio duration with ffmpeg in CI. | Implemented (1 test pack) | NT, RB |
| FR-14 | **Speaking practice with AI grading.** The user records an answer for Part 1/2/3. The audio is stored privately and graded on FC, LR, GRA and Pronunciation. | S | Backend: `POST /speaking/submit` stores audio and returns criterion bands (Gemini multimodal). Frontend: `/speaking` must allow recording once `SPEAKING_AVAILABLE=true`. | **Implemented (gated)**: the backend is live, but the UI flag `SPEAKING_AVAILABLE = false` shows "temporarily unavailable" | NT (UI), RB (grader) |
| FR-15 | **Speaking ML pipeline.** Whisper ASR (faster-whisper) → fluency features (speech rate, pauses, fillers, repairs) → regressors that predict a band, as an alternative or complement to LLM audio grading. | C | `ml.benchmark_asr` reports WER per model size. `ml.train_speaking` reports MAE/QWK on a speaker-disjoint split against the mean baseline (Section 9, E2). Unit tests `test_ml_asr.py`, `test_ml_speech_features.py`, `test_ml_train_speaking.py` pass. | Research | NT |
| FR-16 | **Adaptive practice.** Item difficulty is estimated with a Rasch/1PL model, mastery per question type with Bayesian Knowledge Tracing, and next items are ranked with an explainable score that handles cold start. | C | `ml.evaluate_adaptive` reports AUC on a chronological split for IRT, BKT and blend against the error-rate baseline (Section 9, E3). Tests `test_ml_irt.py`, `test_ml_knowledge_tracing.py`, `test_ml_recommendation.py`, `test_ml_evaluate_adaptive.py` pass. | Research | NT |
| FR-17 | **Vocabulary builder.** The user saves words (also from the reading text), gets AI enrichment (meaning, translation, synonyms, better alternatives, example), marks words for training and takes a daily quiz. | S | `POST /vocabulary/words`, `POST /vocabulary/words/{id}/enrich`, `GET /vocabulary/daily-quiz` and `POST .../submit` work. AI calls count against the daily AI budget (`test_vocabulary.py`, `test_vocabulary_quota.py`). *Not confirmed by interviews (not discussed).* | Implemented | RB |
| FR-18 | **Mistake notebook, history and analytics.** The user can browse saved mistakes (mark them as reviewed), see all past attempts across skills, and view band trajectory, weaknesses, recurring mistakes and streak. | S | `/mistakes`, `/history` and `/analytics` load from `/learning/mistakes`, `/history`, `/analytics/*`. Pages with no data show empty states, not invented numbers. | Implemented | RB |
| FR-19 | **Free-tier quota for AI gradings.** Each user gets a limited lifetime number of free AI reviews (production: 2 Writing, 2 Speaking) and a daily AI budget (default 20 calls). Failed gradings refund the lifetime review but still use the daily budget. | M | `GET /writing/quota` shows remaining reviews. The next submit after the limit returns 403 `ai_free_reviews_exhausted`, and the daily cap returns 429 with `Retry-After`. Parallel requests cannot exceed the budget (`test_ai_quota.py`). | Implemented | RB |
| FR-20 | **Password reset.** The user can reset a forgotten password by email. | C | A reset link is emailed and the old password stops working after reset. | Planned (the "Forgot password?" link currently points back to `/login`) | – |
| FR-21 | **Localised explanations (RU/KZ).** Feedback and explanations are available in Russian/Kazakh. | C | Switching language changes feedback text. *Not confirmed by interviews (not discussed).* | Planned | – |

## 6.2 Non-functional requirements

| ID | Category | Requirement | Measurable acceptance criterion | Verification method | Status |
|----|----------|-------------|----------------------------------|---------------------|--------|
| NFR-1 | Performance | Writing grading finishes fast enough for a single interactive session. | **Target:** p90 end-to-end `/writing/submit` latency ≤ 45 s and p99 ≤ 90 s, warm instance, Gemini 2.5 Flash. Each model call has a 60 s timeout and up to 3 attempts with exponential backoff. The Better Version runs concurrently with grading, not after it. | Server logs/timings over ≥ 30 production submissions (Section 9). Not measured yet. | Implemented (mechanism); target not yet measured |
| NFR-2 | Performance / capacity | Concurrent gradings must not block the API. | At most `MAX_CONCURRENT_GRADINGS` (8) model calls run at once (semaphore). Blocking SDK calls run in a thread pool, so `/health/live` responds during grading. | Code review of `ai/concurrency.py` + load test (planned). | Implemented |
| NFR-3 | Security – authentication | Tokens are signed, expire, and cannot be reused after username changes. | JWT HS256 with required `exp`, `iat`, `sub`. Lifetime 24 h. In production the API refuses to start with a missing, placeholder, < 32-character or previously leaked `SECRET_KEY`. | `test_auth_tokens.py`, `test_ai_safety.py` (CI). | Implemented |
| NFR-4 | Security – OAuth | Google login is protected against code interception and CSRF. | PKCE S256, single-use hashed `state` with expiry, exact redirect-URI match, verified email only (TST-36). | `test_google_auth.py` (CI). | Implemented |
| NFR-5 | Security – abuse | Auth endpoints are rate-limited, and `X-Forwarded-For` is trusted only from configured proxies. | Requests above the auth limit get HTTP 429. A spoofed `X-Forwarded-For` from an untrusted peer is ignored. | `test_ratelimit.py` (CI). Limitation: the counter is per process (documented). | Implemented |
| NFR-6 | Security – secrets & surface | No secrets in the repository. API docs are hidden in production. Containers run as non-root. | `.env` files are ignored by git and only `.env.example` is tracked. `/docs` and `/openapi.json` return 404 when `APP_ENV=production`. Secrets that leaked in git history are blocked at startup. | Repository scan (e.g. gitleaks, planned in CI) + manual check of production endpoints. | Implemented (scan planned) |
| NFR-7 | Privacy | Speaking audio is private, and ML research data is pseudonymous. | Audio is stored outside the public static directory and served only to its owner through an authenticated endpoint (no token in the URL). `ml.export_responses` exports no names, emails or answer text, uses keyed pseudonyms (`ML_EXPORT_KEY` ≥ 32 bytes), and exports are never committed. | `test_deploy_paths.py`, `test_ml_export_responses.py` (CI). Manual check that another user gets 404 for someone else's audio. | Implemented |
| NFR-8 | Reliability – grading integrity | A failed AI grade is never stored as Band 0 and never affects analytics. | If the provider fails, the submission is saved with `status="failed"` and `band=NULL`, no mistakes are recorded, it is excluded from analytics, the lifetime quota is refunded, and the user can retry. The API refuses to start in production if grading would fall back to the mock grader. | `test_writing_retry.py`, `test_ai_quota.py`, `test_ai_safety.py`, `test_gemini_grading.py` (CI). | Implemented |
| NFR-9 | Availability / cold start | The hosting limits of the free tier are stated openly. Readiness reflects real dependencies. | `/health/ready` returns 503 unless the database is reachable and a real grader is configured. The free Render instance sleeps when idle, so the first request after idle can be slow. **Target:** the UI shows a loading state, never an error, during wake-up. Uptime target during the pilot: ≥ 99% of 5-minute checks after warm-up. | External uptime monitor during the pilot (Section 9, E4). | Readiness implemented; monitoring planned |
| NFR-10 | Maintainability | The AI provider can be replaced without touching business logic. Every change passes CI. | Graders implement `WritingGrader`/`SpeakingGrader`/`VocabularyCoach` interfaces. The provider is selected by `AI_PROVIDER` (`mock`/`claude`/`gemini`). CI on every push/PR runs: Alembic single-head check, migration up/down/up on PostgreSQL 16, three content validators, pytest, ESLint, `tsc --noEmit`, Vitest, Next.js build, and production compose validation. | `.github/workflows/ci.yml` must pass before merge. | Implemented |
| NFR-11 | Usability – mobile | All core flows work on a 390 px wide phone screen without horizontal scrolling. | Landing, login/register, writing editor, result, dashboard and Reading review are usable at 390×844 (iPhone 12–15 class). Navigation collapses into a menu. | Manual check on the device sizes in Section 8; planned Playwright viewport tests (Section 9). | Partially verified (public pages, Section 8) |
| NFR-12 | Cost | The AI cost per user is capped and predictable. | Free tier = 2 Writing + 2 Speaking lifetime reviews and ≤ 20 AI calls per user per day, enforced atomically in the database. A cheaper "fast" model (`GEMINI_FAST_MODEL`) is used for coaching and rewrites. **Target:** average model cost per graded essay to be measured (Section 9). | `test_ai_quota.py` + Google AI billing export. | Caps implemented; cost per essay not measured |
