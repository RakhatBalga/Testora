# Testora — Operations Runbook

How Testora runs in production and what to do when something goes wrong. The deployment
overview is in [docs/07-architecture.md](07-architecture.md) (section 7.7) and the README.

## Production at a glance

| Part | Where | Notes |
|---|---|---|
| Frontend | Vercel, https://testora.studio | Next.js; `NEXT_PUBLIC_*` variables are inlined at build time, so changing them needs a redeploy |
| Backend | Render web service `testora-api` (Docker, free plan), defined in `render.yaml` | Sleeps after about 15 minutes idle; the first request after that takes about a minute |
| Database | Neon PostgreSQL (free plan) | Compute suspends after 5 minutes idle; limited free CU-hours |
| CI | GitHub Actions (`.github/workflows/ci.yml`) | Jobs: `backend`, `frontend`, `backend-image`, `compose-config` |

### Deploy flow
1. A pull request runs CI. `main` is protected: the checks `backend`, `frontend` and `compose-config`
   must pass, force-push and deletion are blocked. Approvals are not required yet.
2. After the merge, CI runs on `main`. Render has `autoDeployTrigger: checksPass`, so it deploys the
   commit only after the GitHub checks for it pass. Vercel builds the frontend from `main` itself.
3. On every container start `backend/start-render.sh` runs `alembic upgrade head` and then uvicorn.
   A bad migration or bad configuration makes the new instance fail to start; Render only switches traffic to the new
   instance once it passes the health check, so the previous version keeps serving meanwhile.

There is no separate deploy workflow in GitHub Actions.

## Environment variables

Render (backend), as set in `render.yaml`; secrets are `sync: false` and must be entered in the dashboard.

| Variable | Value / purpose |
|---|---|
| `DATABASE_URL` (secret) | Neon connection string, `sslmode=require` |
| `SECRET_KEY` | JWT signing key (generated by Render). In production the API refuses to start with a weak, short or known-leaked key |
| `APP_ENV` | `production`: enables startup safety checks, hides `/docs` and `/openapi.json` |
| `CORS_ORIGINS`, `FRONTEND_URL` | `https://testora.studio` (and `www`) |
| `TRUSTED_PROXY_CIDRS` | Proxies whose `X-Forwarded-For` is trusted for rate limiting. The client IP is the right-most hop not in this list |
| `APP_TIMEZONE` | `Asia/Almaty` (quota day, streaks, daily plan, exam date) |
| `AI_PROVIDER` | `gemini` in production; `mock` is refused when `APP_ENV=production` |
| `GEMINI_API_KEY` (secret) | Required for `gemini` |
| `GEMINI_MODEL` | Examiner model, `gemini-2.5-flash` |
| `GEMINI_FAST_MODEL` | Cheaper model for coach text and rewrites, `gemini-2.5-flash-lite` |
| `QWEN_BASE_URL`, `QWEN_MODEL`, `QWEN_API_KEY`, `QWEN_TIMEOUT_SECONDS` | Planned local Qwen provider (OpenAI-compatible API, e.g. `http://host:11434/v1`). Not set in production; used only with `AI_PROVIDER=qwen` |
| `FREE_WRITING_SUBMISSIONS`, `FREE_SPEAKING_SUBMISSIONS` | Lifetime free reviews per user (2 and 2) |
| `AI_DAILY_ATTEMPTS`, `AI_GLOBAL_DAILY_ATTEMPTS` | Daily AI calls per user (20) and for the whole service (400) |
| `MAX_CONCURRENT_GRADINGS` | Simultaneous model calls (default 8) |
| `SPEAKING_ENABLED` | `false`: Speaking is closed on the server until it launches |
| `STORAGE_BACKEND` | `database`: avatars and audio are stored in PostgreSQL (`stored_files`), because the container disk is ephemeral |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REDIRECT_URI` (secrets) | Google sign-in. `GOOGLE_REDIRECT_URI` must equal the callback registered in Google Cloud |
| `SENTRY_DSN` (secret) | Optional error tracking; see Monitoring |
| `LOG_LEVEL` | `INFO` |

Vercel (frontend): `NEXT_PUBLIC_API_URL` (public API origin; it is also the origin allowed by the
Content-Security-Policy in `next.config.ts`) and `NEXT_PUBLIC_GOOGLE_CLIENT_ID` (same client id as on
Render; without it the Google button is not rendered).

**Google sign-in (FR-2) in production** works only when all four values above are set: the three
`GOOGLE_*` variables on Render and `NEXT_PUBLIC_GOOGLE_CLIENT_ID` on Vercel, followed by a Vercel redeploy.

## Health checks

| Endpoint | Use | Healthy response |
|---|---|---|
| `/health/live` | Liveness (process up). Render polls this path (`healthCheckPath`) | `200 {"status":"alive"}` |
| `/health/ready` | Readiness (database reachable, grader usable) | `200 {"status":"ready", ...}` |
| `/health` | Back-compat liveness alias | `200 {"status":"ok"}` |

`/health/ready` returns `503` if the database is unreachable, or in production if the effective grader
is mock. Render deliberately uses the liveness path: readiness queries the database and would keep the
Neon compute awake around the clock. Point an external monitor at `/health/ready` only at a low
frequency. The frontend pings `/health/live` on the landing and login pages to wake the backend.

## Database

### Migrations
Alembic runs on boot (see above). CI checks that there is a single head, applies and reverses the
migrations on PostgreSQL 16 (upgrade, downgrade, upgrade), and runs `alembic check` so that models and
migrations cannot drift. New migrations must be backward compatible with the previous release, because
the old instance serves traffic until the new one is healthy.

### Backups
Production data lives in Neon (PostgreSQL only: avatars and audio are in the database too). **There is
no scheduled backup yet.** What exists:

- `scripts/backup_prod.sh`: `pg_dump` (custom format, gzip, mode 600) of the database in `DATABASE_URL`,
  with retention pruning. Run it by hand:
  ```bash
  DATABASE_URL='postgresql://...' BACKUP_DIR=./backups RETENTION_DAYS=14 scripts/backup_prod.sh
  ```
  Use a `pg_dump` client of the same major version as the Neon server. Keep dumps encrypted and off the
  repository: they contain user data.
- `.github/workflows/db-backup.yml`: a manual workflow (needs the repository secret `DATABASE_URL`) that
  uploads the dump as an artifact kept for 7 days. The schedule is commented out. The repository is
  public, so treat this as a stop-gap.
- Neon's own point-in-time restore window on the free plan is short; check the Neon console for the
  current limit before relying on it.

**Restore** (destructive: existing objects are dropped). Prefer a new Neon branch or a scratch database:
```bash
DATABASE_URL='postgresql://<target>' scripts/restore_prod.sh backups/testora_db_YYYYmmddTHHMMSSZ.dump.gz --yes
# a target that looks like production additionally needs --target-is-prod
```
Test a restore into a scratch database before you need it.

## Content import and validation

Content packs live in `backend/content/`. Validate before importing into any persistent database
(from `backend/`):

```bash
python -m content_tools.validate_reading      # 10 tests, 400 questions, evidence quotes verbatim
python -m content_tools.validate_listening    # needs ffprobe for the real audio duration
python -m content_tools.validate_writing
python -m content_tools.importer              # idempotent: existing items are skipped
python -m content_tools.importer --replace    # overwrite matching items without user attempts
```

The importer skips files under `_`-prefixed folders (`content/_examples/`). Running the import twice
should report only skipped items the second time. Legacy/demo Reading tests are hidden from the public
catalogue unless their titles match `IELTS Academic Reading - Test NN`. Do not delete tests that have
attempts attached; historical attempts and review pages must stay available by id.

Demo data for local work: `python -m scripts.seed.seed_demo` (refuses `APP_ENV=production` and non-local
databases unless forced).

## Monitoring

Logs are structured and carry a request id (`X-Request-ID` response header). Key loggers:
`testora.ai.gemini`, `testora.writing`, `testora.speaking`. Read them in the Render dashboard.

| Signal | Where / how | Alert when |
|---|---|---|
| Grading failures | `WARNING` from `testora.{writing,speaking}` ("saved as failed") | rate spikes |
| Gemini retries/errors | `WARNING` from `testora.ai.gemini` | sustained retries |
| Auth failures / abuse | `429` responses | sustained 429s |
| Budget exhausted | `503` from the global daily AI budget | any |
| Readiness | `/health/ready` non-200 | any (low-frequency external monitor) |

Error tracking: set `SENTRY_DSN` **and** add `sentry-sdk` to `backend/requirements.txt`; the package is
not installed in the production image today, so the variable alone does nothing.

## Cost and abuse protection

- Auth endpoints and AI endpoints have per-route rate limits. Limits are in-process (per worker), which is
  the effective cap while Render runs a single instance.
- Per-user lifetime free reviews, a per-user daily AI budget and a global daily AI budget
  (`AI_GLOBAL_DAILY_ATTEMPTS`, table `ai_global_budget`) are reserved atomically. When a budget is
  exhausted the API fails closed with `503`/`429`.
- Concurrent gradings are capped (`MAX_CONCURRENT_GRADINGS`). Request bodies above 1 MB return `413`;
  essay and upload sizes are bounded (`MAX_WRITING_CHARS`, `MAX_AUDIO_UPLOAD_MB`).
- A Writing submission stuck in `pending` is reconciled after `GRADING_STALE_MINUTES` (10) with a quota refund.

## Rollback

1. **Application code (backend):** in the Render dashboard open the service, Events, and roll back to the
   previous successful deploy, or revert the commit on `main` (Render redeploys after the checks pass).
2. **Frontend:** in the Vercel dashboard promote the previous deployment.
3. **Database migrations:** roll back only if the new release ran a migration that the old code cannot
   tolerate. Each migration has a tested `downgrade()`:
   ```bash
   cd backend && DATABASE_URL='postgresql://...' alembic downgrade -1
   ```
   Prefer a forward fix over a downgrade when a migration dropped or rewrote data; restore from a backup
   if data was lost. Order matters: the old image does not know the newer
   revision, so if a migration has to be reversed, downgrade the database first and then roll the code back;
   otherwise `alembic upgrade head` fails on start.
4. Confirm `/health/live` and `/health/ready` return `200`, then log in and submit a test essay.

## Incident response

1. **Detect:** failed deploy, readiness down, grading-failure spike, 5xx surge, a user report.
2. **Triage:** check `/health/ready` (database and grader), the Render logs for the relevant `testora.*`
   logger, and the latest deploy.
3. **Classify**
   - Backend asleep: the first request after idle is slow; wait about a minute and retry.
   - Database down or suspended: Neon wakes on connect; check the Neon console and quotas
     (`pool_pre_ping` recovers transient drops).
   - Gemini failing: failures are saved as `failed` (no bogus grades) and users can re-submit; check the
     key and quota, and consider a status notice.
   - Auth or AI abuse: confirm the 429s and budgets are working; lower the limits if needed.
4. **Mitigate:** roll back (above) if the incident correlates with a release.
5. **Recover and verify:** readiness green, error rate normal.
6. **Post-incident:** short write-up with timeline, root cause and follow-ups.
